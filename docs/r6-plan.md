# R6 — совместимый HTTP API и сырое воспроизведение

Статус: `done, not committed`. Обновлено: `2026-09-23`.

Цель этапа — чтобы существующие клиенты TorrServer работали с клиентским
ядром Rustorr без изменений. Источник истины — наблюдаемое поведение
зафиксированного TorrServer MatriX.145
(`2c7fa43b9ac64a9eda27314c0b6791518497f188`) и воспроизводимый корпус
чёрного ящика. Исходный код эталона может объяснить наблюдение, но не заменяет
его.

Текущее состояние и команды продолжения находятся в
[`r6-continuation.md`](r6-continuation.md).

## Граница этапа

В R6 входят:

- `/echo`; действия с торрентами `add/get/set/rem/list/drop/wipe`;
  multipart-загрузка;
- сырые `GET`/`HEAD` через `/stream[/*fname]` и `/play/:hash/:id`;
- полные, одиночные/открытые/суффиксные/multipart-диапазоны, `416`, условные
  запросы, ETag, Last-Modified, MIME и заголовки Kodi/DLNA;
- индивидуальные, stream и объединённые M3U, Unicode-пути, внешние дорожки
  VLC, ForkPlayer `fn=file.m3u`, `fromlast` и абсолютные URL;
- документ настроек из 41 поля, просмотренное, снимки кэша и runtime-эффекты
  `CacheSize`, `PreloadCache`, `RemoveCacheOnDrop`,
  `TorrentDisconnectTimeout`, `TrackTimecode`, `MergeAllM3U`;
- BasicAuth из `<data-dir>/accs.db`, CORS, WAF и доверенное
  forwarded-расположение;
- миграции SQLite для настроек/просмотренного/каталога и списков WAF.

Не входят:

- R7: интеграции поиска/Torznab/TMDB/хранилищ, GStreamer, ffprobe, MCP,
  DLNA/Bonjour/MSX и WebDAV/FUSE;
- R9: встроенный TLS, HTTPS-редирект, маршруты service/install и устаревшие
  алиасы CLI/env;
- `/shutdown`, `/download/:size` и веб-ресурсы;
- вытеснение на уровне кусков, пока движок и seam хранилища не дают
  безопасной эквивалентной реализации.

Все отложенные HTTP-сценарии в машиночитаемом виде описаны в
[`tools/contract/deferred-routes.json`](../tools/contract/deferred-routes.json):
у каждой записи есть владелец, причина, этап продолжения и признак
ожидаемости wire diff.

## Архитектура

`rustorr-lifecycle::ClientCore` — малый объектно-безопасный порт клиентского
ядра. HTTP зависит только от этого порта; production-адаптер —
`TorrentCoordinator`, unit-тесты HTTP используют `InMemoryClientCore`.
Координатор остаётся единственным владельцем согласованного изменения движка,
кэша и SQLite.

Порядок разрушительной операции жизненного цикла сохраняется: остановить и
дождаться prefetch, проверить закрепления воспроизведения, удалить сессию
движка, затем менять кэш и SQLite. Ошибка до последнего шага не должна
оставлять частичного изменения.

Живой реестр отделён от каталога SQLite:

- `add` создаёт живую сессию; `save_to_db`/`save` делает запись постоянной;
- `drop` выгружает сессию, оставляет каталог и применяет
  `RemoveCacheOnDrop`;
- `rem` удаляет сессию, кэш и каталог, но не просмотренное;
- `wipe` применяет семантику удаления ко всем живым и сохранённым торрентам.

Порт движка раздельно выражает добавление источника, разбор metainfo,
метаданные/файлы, runtime-статус, создание читателя и удаление сессии. HTTP
DTO повторяет правила опускания/null эталона и индекс файла, начинающийся с
единицы; индексы движка внутри доменной границы остаются начинающимися с нуля.

API кэша содержит динамический мягкий лимит, снимок торрента, завершённые
куски и диапазоны активных читателей. Закрепление активного читателя важнее
мягкого лимита; освобождение последнего закрепления повторно запускает
соблюдение лимита.

## HTTP/access-конвейер

Маршруты собираются до access middleware. Наблюдаемый порядок:

1. tracing;
2. WAF по реальному пиру сокета;
3. CORS, доверенное forwarded-расположение и распознавание исключений auth;
4. BasicAuth для управляющих маршрутов;
5. восстановление после паники.

Forwarded host/proto принимаются только от CIDR из
`RUSTORR_TRUSTED_PROXIES`; по умолчанию — loopback. WAF никогда не использует
forwarded IP клиента. При `--http-auth`/`RUSTORR_HTTP_AUTH` отсутствующий,
пустой или некорректный `accs.db` останавливает запуск, учётные данные не
попадают в лог. Управляющие маршруты закрыты; маршруты play и
индивидуальных плейлистов, которыми в эталоне можно делиться, сохраняют
исключения.

## Настройки и сохранение

На новой БД cache-size процесса задаёт начальный `CacheSize`; после
начальной инициализации источником истины становится SQLite. `set` и `def`
применяют runtime-настройки без перезапуска процесса.

Как и MatriX.145, который при каждой смене настроек переподключает
торрент-клиент, `set` и `def` после применения новых настроек выгружают все
живые торренты по семантике `drop`: несохранённый исчезает из `list`,
сохранённый возвращается к строке каталога (`stat 5`). Сознательное
отклонение: торрент с активным читателем остаётся загруженным (в лог пишется
предупреждение), тогда как эталон оборвал бы поток. Закрепление читателя
важнее паритета этого побочного эффекта.

Поля transport/engine, storage-backend, интеграций, TLS, `ReaderReadAHead` и
`ResponsiveMode` точно сохраняются и возвращаются, но не имитируют
отсутствующий runtime-эффект. Это явные ограничения R7/fork/R9. Учётные
записи остаются секретом развёртывания в `accs.db`, вне миграций SQLite.

## Доказательство совместимости

`tools/contract/scenarios.json` фиксирует изолированную подготовку/очистку,
сырые тела, дайджесты и единственный объявленный в манифесте набор
динамической нормализации. Снимок недействителен при любой транспортной
ошибке или `status: null`. Герметичный профиль использует статическую
внутреннюю сеть Docker и один раз перед корпусом создаёт свежие трекер, сидер
и цель; состояние цели очищается до и после каждого сценария. Готовность по
метаданным отделена от готовности пиров для воспроизведения.

Проверяются отдельные профили direct, BasicAuth и reverse proxy.
Семантический diff должен давать:

- ноль core-различий;
- ноль ошибок запросов/транспорта/управления;
- совпадающие дайджесты тел/диапазонов;
- отложенные различия, в точности совпадающие с allowlist;
- отсутствие новых правил нормализации без отдельного наблюдения эталона.

Регрессия включает `tools/r4.sh check`, тесты feature, обе сборки под
Linux-цели, Docker smoke, функциональные гейты и гейты целостности R1 и пробу
перезапуска с `save_to_db:true`. Принятое отклонение R5 `netem-delay-loss`
переносится как открытое: R6 не утверждает, что этот гейт пройден.

## Критерий выхода

R6 получает `done`, только когда снимки direct/auth/proxy действительны,
core diff равен нулю, сырые дайджесты совпадают, регрессия зелёная, а каждый
пробел R7/R9 совпадает с allowlist. Любое незакрытое различие оставляет этап в
`in progress` и записывается в handoff с точным артефактом и следующим
действием.

Итог 2026-09-23: снимки direct/auth/proxy действительны на одном манифесте,
core diff равен нулю, отложенные различия совпадают с allowlist, матрица
перезапуска совпадает с эталоном, регрессия зелёная. `netem-delay-loss` из R5
остаётся открытым. Реестр доказательств и команды воспроизведения — в
[`r6-continuation.md`](r6-continuation.md).
