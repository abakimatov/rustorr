# Продолжение R9

Статус: `in progress` с 2026-09-25. План и решения — в
[`r9-plan.md`](r9-plan.md).

## R9.1 — сервер

- `rustorr health [--timeout 5]`: `GET /echo` на первом адресе
  `--listen` (для `0.0.0.0`/`::` — loopback); успех — любой HTTP-ответ
  ниже 500 (401 за авторизацией и редирект на HTTPS тоже значат «жив»).
  В образе — `HEALTHCHECK` на неё: curl в образе нет.
- `rustorr backup <файл>`: `.tar.gz` с согласованным снимком базы
  (`VACUUM INTO` на соединении только для чтения — сервер может работать
  дальше, миграций нет), `accs.db`, `trackers.txt`, `server.pem`/`server.key`
  (если есть) и манифестом `backup.json` (формат, версия, схема, время,
  файлы). Кэш и каталог движка (временные файлы и кэш DHT) не входят.
  Пишется во временный файл рядом и переименовывается; права 0600.
- `rustorr restore <файл> [--force]`: распаковка во временный каталог
  внутри каталога данных (только известные имена файлов, без путей);
  манифест и схема проверяются (`rustorr_state::inspect`: база Rustorr, не
  новее сборки); существующая база без `--force` не трогается; с
  `--force` прежние файлы состояния (включая WAL) заменяются.
  Сервер должен быть остановлен.
- `rustorr-state`: `snapshot`, `inspect`, `SCHEMA_VERSION`; проверка
  «база Rustorr и схема не новее» вынесена из миграций.
- Предупреждение в логе при старте: авторизация выключена, а сервер
  слушает адрес, доступный другим машинам.
- Секреты: access-лог (формат `--weblogpath` MatriX пишет тело запроса)
  маскирует в JSON-телах строковые значения полей `*key`, `password`,
  `secret`, `token` (`APIKey` TMDB, `Key` Torznab, `key` проверки
  индексатора); тела без таких полей пишутся байт в байт. Трассировка
  HTTP пишет только метод и путь; URL прокси с паролем в лог не попадает
  (ошибки разбора показывают только схему); конфигурация целиком не
  логируется.

Проверка: `tools/r4.sh check` — 377 Rust-тестов (бэкап и восстановление,
отказ без `--force`, отказ от чужих записей в архиве, health, снимок базы в
работе, отказ от чужой и более новой базы, маскирование).

## R9.2 — TLS

- Флаги (и переменные `RUSTORR_*`): `--ssl`, `--ssl-port`, `--ssl-cert`,
  `--ssl-key`, `--force-https`. Поведение `server.go`/`web/server.go`
  MatriX: порт — флаг, иначе `SslPort` из настроек, иначе 8091; пути из
  флагов и порт из флага сохраняются в настройки (кроме режима только для
  чтения); без сертификата — самоподписанный `server.pem`/`server.key` в
  каталоге данных (ECDSA P-384, год, `localhost` и адреса интерфейсов,
  O=Rustorr; ключ с правами 0600); сертификат просрочен, не читается или
  ключ не от него — предупреждение и новый самоподписанный. HTTPS слушает
  на каждом адресе `--listen` с этим портом; `--force-https` без `--ssl` —
  ошибка запуска.
- `--force-https`: обычные сокеты отвечают `307` на
  `https://<host>[:порт]<путь>?<query>` (порт 443 опускается), тело —
  как у Go `http.Redirect`. Отклонение: эталон экранирует уже
  экранированный путь второй раз (`%20` → `%2520`), ломая имена с
  пробелами и кириллицей; Rustorr сохраняет путь как есть.
- Реализация: `Listeners` в `rustorr-http` различает обычные, TLS- и
  редирект-сокеты; TLS — свой `axum::serve::Listener` (рукопожатия в
  отдельных задачах, таймаут 10 с), обёрнутый `tap_io`, чтобы
  `ConnectInfo<SocketAddr>` работал как у TCP; rustls на aws-lc-rs,
  TLS 1.2/1.3, ALPN `http/1.1`. Сертификат — `rcgen`, проверка срока —
  `x509-parser`; OpenSSL в дерево не попадает.

Проверка: 382 Rust-теста (редирект, цель редиректа, самоподписанная пара
создаётся один раз и запоминается, порт из флага сохраняется, чужой ключ
отвергается и заменяется); вживую — HTTPS по TLS 1.3, `307` с HTTP,
`rustorr health` за редиректом, бэкап с сертификатом.

## R9.3 — деплой

Инструкция оператора — [`deploy.md`](deploy.md).

- `tools/deploy.sh [--gst|--ffprobe] [--tag|--image] [--dir] [--ssh] <user@host>
  <команда>`: `deploy`, `rollback`, `restart`, `status`, `logs`, `backup`,
  `download`, `restore`, `password`, `cert`. Скрипты на сервере идут через
  `sh -c` (не зависят от login-shell), данные в них — через stdin, пароль в
  аргументы процессов не попадает.
- Образ собирается `buildx` под `uname -m` сервера и уходит `docker save |
  gzip | ssh … docker load`; уже загруженный образ не отправляется. По
  умолчанию — без `ffmpeg` (≈180 МБ против ≈740 МБ): `docker save` передаёт
  образ целиком при каждом обновлении; `--ffprobe` добавляет его для `/ffp`,
  `--gst` — вариант с GStreamer.
- На сервере: `~/rustorr` (`compose.yaml` из `deploy/`, `.env` из
  `deploy/env.example` — только при первой установке, `current`/`previous`,
  `upgrade-backup`, `backups/` 0700), том `rustorr_data` (создаёт
  `compose create`, чтобы у тома были метки compose). Порты: HTTP/HTTPS на
  `RUSTORR_BIND` (0.0.0.0 или 127.0.0.1 за прокси), пиры 6881 TCP+UDP;
  логи JSON с ротацией `json-file`; `stop_grace_period` 15 с.
- Первая установка с `RUSTORR_HTTP_AUTH=true` заводит `admin` со случайным
  паролем через `rustorr passwd` и выводит его один раз.
- Обновление: бэкап `pre-upgrade-*`, `compose up`, ожидание `healthy`
  (провал сразу, если контейнер перезапускается); при провале — откат.
  Откат: предыдущий образ на текущих данных, а если он не поднимается
  (схема новее) — восстановление бэкапа перед обновлением. Хранятся
  текущий и предыдущий образы.
- `cert <цепочка> <ключ>`: файлы в том как `tls-cert.pem`/`tls-key.pem`
  (отдельно от самоподписанных `server.pem`/`server.key`, чтобы
  отвергнутая пара не затёрла файлы оператора), HTTPS в `.env`, перезапуск
  и проверка, что сервер принял сертификат.
- Бинарник: `rustorr passwd <user>` (пароль со stdin, `accs.db` 0600);
  бэкап включает и `tls-*.pem`; сообщение об отвергнутом сертификате
  объясняет требования (X.509 v3, RSA или EC с именованной кривой).

## R9.4 — проверка на «удалённой» машине

`tools/r9.sh smoke`: контейнер `docker:28-dind` с `sshd`
(`tools/r9/Dockerfile.remote`) как чистый сервер; `tools/deploy.sh` по SSH
по ключу. Шаги и что проверяется:

1. Первая установка: пароль выведен; API без пароля — `401`; `.torrent`
   загружается; пароля нет в логах.
2. Обновление: `current` — новый образ, есть `pre-upgrade`-бэкап, торрент
   на месте.
3. Перезапуск, 4. откат — торрент на месте.
5. Откат после «новой схемы» (обновление, удаление торрента, `user_version`
   базы = 99): предыдущая версия не открывает базу → восстановлен бэкап
   перед обновлением, торрент вернулся.
6. Сломанный образ (`--image`, выходит при старте): деплой завершается
   ошибкой и сам откатывается.
7. Бэкап, скачивание, `wipe`, восстановление из скачанного файла.
8. Смена пароля: новый принимается.
9. Свой сертификат: X.509 v1 от LibreSSL — `cert` сообщает об отказе;
   v3 с именованной кривой — HTTPS отдаёт именно его (`s_client`), он
   входит в бэкап.

Прогон — около 3 минут; `R9 smoke: OK`.

Проверка: `tools/r4.sh check` — 383 Rust-теста; `tools/r4.sh smoke` —
образы `linux/arm64` и `linux/amd64` собираются, arm64 запускается,
перезапускается и открывает базу; `tools/r9.sh smoke` — OK.
