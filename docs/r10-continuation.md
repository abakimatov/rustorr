# Продолжение R10

Статус: `in progress` с 2026-09-25. План — [`r10-plan.md`](r10-plan.md).

## R10.1 — производительность

Стенд R1 (`tools/baseline/r1.sh`, методика и сценарии —
[`benchmark-baseline.md`](benchmark-baseline.md)), образ Rustorr с
`r5-test-control` (детерминированное вытеснение). Перед замером стенд
должен собрать свой образ: `RUSTORR_R1_TARGET=rustorr tools/baseline/r1.sh
build` — контрактный кандидат и стенд замеров делят имя
`rustorr-r1-rustorr`, и `run` без `build` запускает чужой образ (без
канала управления вытеснением). Контрактный стенд (внутренняя сеть
`baseline`) перед R1 останавливается: `docker compose -f
docker-compose.baseline.yml -f docker-compose.r2-hermetic.yml down
--remove-orphans`.

### Найдено и исправлено: magnet ждал сида 10–20 с

Метрика `metadata_discovery_ms` (от ответа `add` до «работает и есть
подключённый сид») — 11,1 с против 6,1 с у MatriX. Отладочный лог librqbit:
magnet-метаданные приходят по отдельным соединениям с пирами, и через
40 мс librqbit подключается к тем же пирам заново для самого торрента, с
тем же peer id; Transmission ещё держит первое соединение и сбрасывает
дубликат (`Connection reset by peer`), а librqbit повторяет попытку к этому
пиру только через 10–20 с. У anacrolix метаданные и торрент — один объект,
дубликата нет.

Исправление (`rustorr-engine`, `resolve_magnet`): magnet сначала
разрешается отдельно (`list_only`, librqbit отдаёт байты метаданных и
увиденных пиров), 500 мс на закрытие тех соединений, затем торрент
добавляется из байтов с этими пирами (`initial_peers`) и трекерами
magnet-ссылки. Проба на стенде: сид подключается через 0,6 с после
ответа `add` (было 11–16 с). Тест движка:
`a_magnet_resolves_then_downloads_from_the_peer_it_found`.
