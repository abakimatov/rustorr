# Архитектура R4

Статус: `accepted 2026-09-21`.

## Компоненты и владение

| Компонент | Владеет | Не владеет |
| --- | --- | --- |
| `rustorr-domain` | хеши, индексы, диапазоны, доменные ошибки | IO и сериализацией |
| `rustorr-engine` | живой сессией librqbit, транспортом пиров, файлом DHT | политикой кэша, продуктовым состоянием |
| `rustorr-cache` | байтами кусков, резидентностью, LRU и закреплениями | жизненным циклом движка |
| `rustorr-state` | `rustorr.db`, схемой и продуктовыми записями | живыми торрентами |
| `rustorr-http` | маршрутами, DTO, отображением HTTP-ошибок | конкретными реализациями |
| `rustorr-server` | конфигурацией и сборкой запуска/остановки | переиспользуемой политикой |

Допустимый граф зависимостей проверяется `tools/r4.sh boundaries`;
нормативное решение — [ADR 0005](adr/0005-crate-boundaries-and-engine-isolation.md).

## Жизненный цикл выполнения

При запуске устанавливаются обработчики сигналов, привязывается HTTP,
создаётся каталог данных, открывается SQLite, создаётся кэш, затем стартует
движок. При остановке сначала останавливается HTTP, затем движок, затем
освобождаются кэш и состояние. Дренаж HTTP ограничен
`RUSTORR_SHUTDOWN_GRACE` (по умолчанию 5 секунд); у внешнего runtime Tokio
отдельный двухсекундный дедлайн остановки.

HTTP-слои упорядочены снаружи внутрь: tracing, будущие механизмы контроля
доступа (CORS/WAF/auth), затем перехват паник. Так слой доступа R6 остаётся
вне ответа на панику и виден для tracing.

## Каталог данных

```
<data>/
  rustorr.db             источник истины SQLite
  engine/dht.json        удаляемый кэш маршрутизации DHT librqbit
  engine/scratch/        временные файлы движка
  cache/<hash>/<file>    хранилище кусков, принадлежащее Rustorr
```

`rustorr.db` использует WAL и идентификаторы схемы/приложения (ADR 0006).
Вытеснение кэша выполняется на уровне торрента: координатор в R5 должен
удалить сессию до удаления записи кэша, потому что удаление байтов из-под
живого торрента может молча испортить чтение (ADR 0004).
