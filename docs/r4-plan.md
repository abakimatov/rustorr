# R4 — архитектурный skeleton Rustorr: план

Статус: `done` (шаги 1–9 выполнены). Обновлено: `2026-09-21`.

Состояние для новой сессии, команды и точный следующий шаг —
[`r4-continuation.md`](r4-continuation.md).

Входные условия выполнены: R3 закрыт, [ADR 0003](adr/0003-bittorrent-engine-selection.md)
(`adopt librqbit 9.0.1` за адаптером) и [ADR 0004](adr/0004-cache-eviction-seam.md)
(кэш Rustorr на storage-seam, вытеснение по торренту) приняты.

## Объём

R4 — каркас без функционального наполнения. Он фиксирует crate-границы,
ownership данных, error boundaries и сборку; поведение торрентов, кэша и API
наполняется в R5/R6.

Входит:

- Cargo workspace, собираемый на Linux `x86_64` и `aarch64`;
- crate-границы с интерфейсами (traits и доменные типы) и минимальными
  реализациями, достаточными для запуска;
- smoke server: бинарник и Docker-образ поднимаются, открывают состояние,
  создают engine session и отвечают на `GET /echo`;
- ADR для необратимых решений.

Не входит (принято 2026-09-21):

- `/torrents`, `/stream`, `/play`, плейлисты и остальной контракт R2 — R6;
- add/load/drop, чтение диапазонов и связывание кэша с движком — R5;
- прогон `tools/baseline/r1.sh` против Rustorr — перенесён в R5 вместе с двумя
  необъяснёнными ~20-секундными случаями из R3;
- UI (R8), интеграции (R7), TLS, упаковка бинарника как самостоятельного
  артефакта и multi-arch публикация (R9).

## Решения стека

| Область | Решение | Основание |
| --- | --- | --- |
| Async runtime | `tokio` | librqbit построен на tokio; второй runtime не нужен |
| HTTP | `axum 0.8` + `hyper 1` + `tower` | уже в дереве зависимостей librqbit; middleware для auth/WAF/CORS — tower layers |
| Сериализация | `serde` + `serde_json`, отдельные DTO на HTTP-границе | R2 требует точности null/отсутствия поля, int/float и `[]`; доменные типы не сериализуются напрямую в ответ |
| Persistence | SQLite через `rusqlite 0.40` с `bundled` | выбор пользователя; online backup API нужен в R9; без системной зависимости |
| Ошибки | `thiserror` в библиотечных crates, `anyhow` только в бинарнике | типы ошибок движка не пересекают границу адаптера |
| Логи/трейсы | `tracing` + `tracing-subscriber` (text/JSON) | уже в дереве librqbit; метрики — R9 |
| Конфигурация | `clap` (флаги + env) | флаги совместимости с CLI TorrServer — отдельный вопрос R9 |
| Toolchain | Rust `1.90.0`, edition 2024 | тот же pin, что у spike |
| Движок | `librqbit = "=9.0.1"` с `default-features = false, features = ["rust-tls"]`, общий `Cargo.lock` в корне | условие 5 ADR 0003; выбор features — по аудиту шага 3 |

## Crate-границы

```
crates/
  rustorr-domain   типы без IO: InfoHash, FileIndex, ByteRange, PieceIndex,
                   доменные ошибки
  rustorr-engine   trait движка в доменных типах + единственная реализация
                   на librqbit; мост StorageFactory → PieceStore кэша
  rustorr-cache    residency index, torrent-scoped LRU с pins, PieceStore
                   (MemoryStore для RAM-only, DiskStore для SSD), громкая
                   ошибка на отсутствующем диапазоне
  rustorr-state    SQLite: каталог торрентов, settings, viewed; миграции
  rustorr-http     axum router, DTO, маппинг ошибок в ответы TorrServer,
                   access layers (auth/WAF/CORS) как tower-слои
  rustorr-server   бинарник `rustorr`: конфигурация, composition root,
                   observability, graceful shutdown
```

Правила зависимостей:

- `rustorr-domain` не зависит ни от чего внутри workspace.
- **Только `rustorr-engine` зависит от `librqbit`/`librqbit-core`** (условие 1
  ADR 0003). Проверяется автоматически по **прямым** зависимостям
  (`cargo metadata`): ни у одного другого crate `librqbit*` не может быть в
  `dependencies`; нарушение валит `check`. Транзитивно librqbit компилируется
  у каждого, кто зависит от `rustorr-engine`, — это ожидаемо и границу не
  нарушает: без прямой зависимости назвать тип движка нельзя, а публичный API
  `rustorr-engine` выражается только доменными типами (проверяется ревью).
- `rustorr-cache` не знает о librqbit и о движке вообще. Он определяет
  собственный trait `PieceStore`; `rustorr-engine` зависит от `rustorr-cache`
  ради тонкого моста, реализующего librqbit
  `StorageFactory`/`TorrentStorage` поверх `PieceStore`. Так seam из ADR 0004
  остаётся на стороне Rustorr и переживает замену движка.
- `rustorr-http` работает с engine, cache и state через их trait-объекты;
  конкретные реализации создаются и связываются только в `rustorr-server`.
  Trait и его реализация живут в одном crate, поэтому `rustorr-http`
  зависит от crate целиком. Если сборка тестов HTTP из-за librqbit станет
  узким местом, порт выносится в отдельный crate — это обратимо и без ADR.
- Интеграции (DLNA, Bonjour, MCP, WebDAV/FUSE, GStreamer, ffprobe, Torznab,
  TMDB) и UI получают crates, когда начнётся R7/R8. В R4 граница фиксируется
  в архитектурном документе; пустые crates не создаются.
- `tools/engine-spike` остаётся отдельным проектом вне workspace — это
  инструмент доказательств R3, а не production-код.

## Ownership данных

| Данные | Владелец | Правило |
| --- | --- | --- |
| Каталог торрентов, settings, viewed | `rustorr-state` | единственный источник истины после рестарта |
| Живые сессии и пиры | `rustorr-engine` | не персистятся; persistence и fast-resume librqbit выключены, потому что fast-resume доказан только для той же output-директории |
| Кэш маршрутной таблицы DHT (`<data>/engine/dht.json`) | `rustorr-engine` | можно удалять без потерь; путь задаётся явно внутри data dir, потому что умолчание librqbit — OS-каталог кэша |
| Байты pieces на диске/в RAM и residency index | `rustorr-cache` | вытеснение только целым торрентом (ADR 0004); чтение отсутствующего диапазона — ошибка, не нули |
| Pins/активные просмотры | координатор жизненного цикла | вводится в R5; в R4 — только API pin/unpin кэша |
| Конфигурация процесса | `rustorr-server` | передаётся в crates явными структурами, без глобального состояния |

## Границы ошибок

- Каждый библиотечный crate экспортирует свой `Error` (`thiserror`); ошибки
  librqbit конвертируются внутри `rustorr-engine` и наружу не выходят.
- `rustorr-http` — единственное место, где ошибка становится HTTP-статусом и
  телом. Таблица маппинга в R4 покрывает только skeleton-маршруты; форма
  тела ошибки берётся из корпуса R2, а не придумывается.
- Паника в обработчике запроса не роняет процесс (tower catch-panic layer).
- Ошибки старта (нет доступа к data dir, миграция SQLite, bind порта) —
  понятное сообщение и ненулевой код выхода.

## Сборка и платформы

- На хосте нет `cargo`/`rustc`; сборка и проверки идут в Docker
  (`rust:1.90-bookworm`). `target/` держать в named volume, а не в bind mount:
  в R3 bind-mounted `cargo check` падал с rustc SIGBUS.
- Хост — `arm64`, поэтому `aarch64` собирается нативно, `x86_64` — через
  `docker buildx` с кросс-компиляцией на `BUILDPLATFORM` (не через QEMU-сборку).
  Запуск `x86_64`-образа для smoke допускается под эмуляцией.
- Target в R4 — `*-unknown-linux-gnu` на bookworm. Статический musl-бинарник
  и аллокатор — решение R9 с замером.
- `openssl` в дерево не допускается. Аудит шага 3: у `librqbit 9.0.1` по
  умолчанию включён `default-tls`, который тянет `openssl` через
  `reqwest/default-tls` и `crypto-hash` (SHA-1). Вместо него включён
  `rust-tls`: `openssl`, `openssl-sys` и `crypto-hash` из дерева исчезают
  (309 crates против 315), а SHA-1 считает `aws-lc-rs`. Нативный код остаётся:
  `aws-lc-sys` (rustls и SHA-1), позже добавится bundled SQLite. Охранная
  проверка лежит в `tools/r4.sh boundaries` и падает, если `openssl` вернётся.

## Шаги

Каждый шаг заканчивается зелёными `cargo fmt --check`,
`cargo clippy --workspace --all-targets --locked -- -D warnings` и
`cargo test --workspace --locked` в Docker.

1. **Workspace и toolchain.** Корневые `Cargo.toml` (workspace, общие
   `[workspace.dependencies]`, lints), `rust-toolchain.toml`, `Cargo.lock`,
   шесть crates-заглушек, `tools/r4.sh` с командами `check`, `test`, `build`,
   `cargo`; `.gitignore` для `target/`. Команда `smoke` добавляется на шаге 8,
   когда есть что запускать.
2. **Домен и ошибки.** Типы `rustorr-domain` и соглашения об ошибках;
   unit-тесты парсинга/валидации (info-hash, диапазоны). Отдельного
   `TorrentId` нет: торрент идентифицируется `InfoHash`, как в API TorrServer;
   внутренний id движка остаётся внутри адаптера.
3. **Engine-адаптер.** Trait движка в доменных типах; реализация на librqbit,
   которая создаёт `Session` с явно заданными session-level опциями и
   проверяет их после создания (условие 3 ADR 0003), корректно
   останавливается. Аудит features librqbit и openssl. Проверка «только
   engine зависит от librqbit» в `tools/r4.sh check`.
4. **Кэш.** `PieceStore` (`MemoryStore` и `DiskStore`), residency index, LRU по
   торрентам с pin/unpin и лимитом размера, entry point вытеснения,
   `pread` с ошибкой на отсутствующем диапазоне. Unit-тесты политики на
   фейковом store без движка. Мост `StorageFactory → PieceStore` в
   `rustorr-engine` реализован и проверен на живой сессии librqbit; его
   подключение к `LibrqbitEngine::start` и `seek-evicted` — R5. Явный
   двухуровневый RAM+SSD store отложен до измерений R5: на Linux page cache
   уже держит недавние данные `DiskStore` в RAM.
5. **Состояние.** Открытие SQLite в data dir, WAL, миграции со схемой v1
   (торренты, settings, viewed), версия схемы в БД; тесты на временной
   директории, включая повторное открытие.
6. **HTTP.** Router, `GET /echo` с версией, маппинг ошибок, tracing запросов,
   catch-panic. Access-слой (auth/WAF/CORS) как пустая заготовка с
   конфигурацией не создаётся: без поведения это мёртвый код; вместо этого
   зафиксированы порядок слоёв и место их вставки (см. `with_layers`). Тесты
   через `tower::ServiceExt::oneshot`.
7. **Сервер.** `rustorr` с конфигурацией (порт, адрес, data dir, лимит кэша
   с документированным значением по умолчанию), composition root, логи,
   graceful shutdown по SIGINT/SIGTERM: HTTP перестаёт принимать запросы,
   engine session останавливается, SQLite закрывается.
8. **Docker и smoke.** Multi-stage `Dockerfile` (сборка → `debian:bookworm-slim`,
   non-root, volume для data dir), `docker-compose.r4-smoke.yml`,
   `tools/r4.sh smoke`: сборка `linux/arm64` и `linux/amd64`, запуск,
   `GET /echo`, `docker stop` → код выхода 0 и запись о штатном завершении,
   повторный старт на том же volume. Дополнительно — capture R2 contract suite
   против skeleton как `candidate` (`RUSTORR_CANDIDATE_BASE_URL`), чтобы
   доказать, что harness адресует Rustorr; ожидаемый diff — всё красное,
   кроме `/echo`, и он записывается как исходная точка R6.
9. **Документы.** ADR, архитектурный документ, handoff.

## ADR этапа

- **ADR 0005 — crate-границы и изоляция движка.** Правила зависимостей выше,
  `PieceStore` как seam кэша на стороне Rustorr, автоматическая проверка.
- **ADR 0006 — SQLite как источник истины состояния.** Выключенная
  persistence librqbit, ownership данных, миграции, основа для backup/restore
  в R9.

Выбор tokio/axum/serde не требует ADR: он вынужден деревом зависимостей
librqbit и обратим на уровне `rustorr-http`.

## Критерии выхода

- `tools/r4.sh check` зелёный: fmt, clippy `-D warnings`, тесты, проверка
  зависимости от librqbit.
- Release-сборка проходит для `linux/arm64` и `linux/amd64`.
- Бинарник и Docker-образ стартуют, отвечают на `GET /echo`, штатно
  завершаются по SIGTERM и повторно стартуют на том же data dir.
- Результат аудита openssl записан.
- R2 capture против skeleton выполнен, diff сохранён как исходная точка R6.
- ADR 0005 и 0006 приняты; handoff добавлен в
  [`implementation-plan.md`](implementation-plan.md).

## Риски

- **Кросс-сборка `x86_64` с нативными зависимостями** (openssl, `aws-lc-rs`,
  bundled SQLite) — самый вероятный блокер шага 8. Снижение: аудит features
  на шаге 3, до Docker-работы.
- **Мост `StorageFactory` может потребовать типы, которых нет в `PieceStore`.**
  Если его нельзя выразить без протечки типов librqbit в `rustorr-cache`, это
  обсуждается до слияния шага 4, а не обходится.
- **Время сборки librqbit под эмуляцией** — поэтому кросс-компиляция вместо
  QEMU-сборки.
- **Соблазн начать R5 внутри R4.** Любая логика чтения торрента, кроме
  создания session, откладывается.

## Прогресс

### Шаг 1 — workspace и toolchain (выполнен 2026-09-21)

- Артефакты: `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `crates/*`
  (шесть заглушек с документацией границ), `tools/r4.sh`,
  `tools/r4/Dockerfile.dev`.
- Проверено: `tools/r4.sh check` (fmt, clippy `-D warnings`, тесты) и
  `tools/r4.sh build` завершаются с кодом 0; бинарник `rustorr` запускается и
  печатает версию. Гейты проверены негативно: намеренное нарушение форматирования
  даёт код 1, нарушение clippy — 101, восстановленное дерево снова 0.
- Решения: `tools/engine-spike` исключён из workspace (`exclude`), иначе cargo
  отказывается собирать его внутри дерева workspace; toolchain закреплён
  `rust-toolchain.toml` (`1.90.0`, edition 2024, resolver 3); `target/` и кэш
  cargo — в named volumes, монтируются только исходники.
- Оговорка: собрано только нативно (`aarch64` на arm64-хосте). Сборка
  `x86_64` — шаг 8.

### Шаг 2 — домен и ошибки (выполнен 2026-09-21)

- Артефакты: `crates/rustorr-domain/` — `InfoHash`, `FileIndex`, `PieceIndex`,
  `ByteRange`, `Error`; `thiserror = "2"` в `[workspace.dependencies]`.
  Соглашения об ошибках записаны в документации crate (`lib.rs`).
- Проверено: `tools/r4.sh check` — код 0, 20 unit-тестов. Мутационная проверка:
  перестановка полубайтов в разборе хеша роняет 3 теста, сдвиг на единицу в
  `FileIndex::from_one_based` — 2 теста; после отката всё зелёное.
- Решения, взятые из корпуса эталона (`20260920T144518Z/reference.json`):
  `file_stats[].id` начинается с **1**, а файлы librqbit — с 0, поэтому
  `FileIndex` хранит нулевую базу и пересекает границу только через
  `from_one_based`/`one_based`; хеш — 40 hex-символов в нижнем регистре, разбор
  принимает и верхний регистр. `TorrentId` не вводится (см. шаг 2 выше).
- Границы: разбор base32 в magnet-ссылках, `Range` заголовков и пределы
  `PieceIndex`/`FileIndex` по числу pieces/файлов остаются за R5/R6, потому что
  зависят от метаданных торрента или HTTP-слоя. `index=0` в запросах эталона
  не характеризован — проверить при реализации `/stream` в R6.

### Шаг 3 — engine-адаптер (выполнен 2026-09-21)

- Артефакты: `crates/rustorr-engine/` (`Engine` и `EngineStatus` — порт;
  `EngineConfig`; `Error`; `LibrqbitEngine` — адаптер),
  `tools/r4/check-boundaries.py`, команда `tools/r4.sh boundaries`, которую
  теперь вызывает `check`.
- Проверено: `tools/r4.sh check` — код 0; 12 тестов адаптера, из них 4 на
  живой multi-thread сессии без сети (без DHT, со слушателем, с DHT, с
  недоступным data dir). Мутации: инверсия флага трекеров роняет 1 тест;
  «забытый» слушатель роняет 2, причём живой тест падает с
  `SettingNotApplied { expected: "Some(0)", actual: "None" }` — то есть
  проверка после старта работает. Стражи границ: `http → librqbit` и
  `cache → engine` дают код 1, возврат `openssl` через `default-tls` — тоже, с
  цепочкой зависимостей.
- Условие 3 ADR 0003. Все session-level опции собираются в одной функции
  `session_options`. Читаются назад и сверяются после старта только DHT и
  порт слушателя (`Session::get_dht`, `listen_addr`). Трекеры, persistence и
  fast-resume из сессии не читаются, поэтому проверяются юнит-тестами на
  самой функции. Per-torrent настройки изоляции адаптер не принимает.
- Находки аудита:
  - `DhtSessionConfig::default()` включает сохранение DHT в OS-каталог кэша
    (`persistence: Some(..)`, `config_filename: None`). Адаптер задаёт путь
    явно внутри data dir; сохранение оставлено, потому что время холодного
    старта — приоритет, а файл можно потерять без последствий. Влияние на
    старт не измерено.
  - `BlockingSpawner` librqbit выносит блокирующую работу с диском через
    `block_in_place`; на current-thread runtime он не падает, а выполняет её
    прямо на единственном потоке и стопорит весь runtime. Сервер должен
    работать на multi-thread runtime (`spawn_utils.rs`).
  - `Session::stop` ждёт секунду безусловно (`sleep(1s)` в самой библиотеке),
    так что остановка сервера занимает не меньше секунды.
  - `axum` в дереве в любом случае: его тянет обязательный `axum-extra`.
- Перенесено в R5: гейты R3 проходили на `default-tls`, то есть на SHA-1 через
  OpenSSL. Продовая сборка считает SHA-1 через `aws-lc-rs`. Результат должен
  совпасть, но доказательство R3 относится к другой сборке; прогон R1 против
  Rustorr выполняется уже на продовой и закрывает это. Для шага 8: сборку
  `x86_64` из-под arm64 ломает скорее всего `aws-lc-sys`, а не `openssl`.
- Зафиксированные версии: `Cargo.lock` засеян lock-файлом spike, поэтому
  транзитивные версии, прошедшие R3, сохранены (расхождений нет; из дерева
  ушли только пакеты OpenSSL-ветки, добавились `tempfile` и его зависимости).

### Шаг 4 — кэш и мост к движку (выполнен 2026-09-21)

- Артефакты: `crates/rustorr-cache/` (`Cache`, `CacheConfig`, `Pin`,
  `PieceStore`, `MemoryStore`, `DiskStore`, `TorrentLayout`, `Error`);
  `crates/rustorr-engine/src/cache_storage.rs` (`CacheStorageFactory`,
  `CacheStorage`) и сквозные тесты `session_tests.rs`; таблица границ и
  правила внешних владельцев в `tools/r4/check-boundaries.py`.
- Проверено: `tools/r4.sh check` — код 0; cache 52 теста, domain 20, engine 25
  (12 адаптер, 8 мост, 5 сквозных на настоящей сессии librqbit по loopback).
  Мутации, каждая убита тестами: `covers ≡ true`, обратный порядок LRU,
  `remove` без проверки pin, двойной подсчёт байт при перезаписи, проглоченная
  ошибка `pread`, непроверяемая длина файла, потерянный `on_piece_completed`,
  неверная длина piece в раскладке.
- Проектные решения:
  - Эвикция двухфазная и управляется снаружи. Кэш только называет
    кандидатов (`eviction_candidates`); координатор R5 сначала удаляет торрент
    из сессии движка, затем вызывает `Cache::remove`, которая отказывает для
    pinned-торрента. Кэш движок не вызывает. Так порядок из ADR 0004 (сначала
    сессия, потом байты) выражен в API, а не в договорённости.
  - Два уровня учёта. Побайтовые записанные диапазоны живут в store (`Extents`)
    и решают, можно ли читать; проверенные pieces — в индексе кэша
    (`on_piece_completed`). Отдельный уровень нужен, потому что librqbit
    проверяет piece чтением до вызова `on_piece_completed`.
  - `Cache::open` идемпотентен для той же раскладки и сохраняет данные:
    librqbit создаёт storage заново при каждом pause/resume и re-add.
  - Recency — логические часы, обновляются чтением и снятием pin, но не
    записью (ADR 0004: «least-recently-read»).
  - `DiskStore` держит записанные диапазоны только в памяти; остатки прошлого
    запуска очищаются при `open`. Сохранение кэша между рестартами — R5.
    Файлы не растягиваются заранее, открываются на каждую операцию.
  - `CacheConfig::PROVISIONAL_CAP_BYTES` = 4 GiB — заглушка, подлежит
    размеру по измерениям R5.
- Подтверждено запуском, а не чтением исходников: initial check librqbit
  переживает пустой кэш (все чтения падают, торрент остаётся рабочим);
  раскладка, выведенная из реальных метаданных, равна заданной вручную;
  `delete` → `Cache::remove` → повторный `add` перекачивает торрент;
  повторный `add` при сохранённом кэше поднимает файл без единого пира.
- Последствие ADR 0004, которое нужно решить в R5: лимит кэша мягкий. Торрент
  с живым просмотром не вытесняется, поэтому один смотримый торрент растёт до
  размера скачанных pieces и может превысить лимит; `CacheStats::over_cap_bytes`
  это показывает. Жёсткая граница возможна только через piece-level
  invalidation, то есть через названный fork trigger.
- Наблюдение для R5 (гипотеза, не вывод): перекачка после эвикции на loopback
  с явно заданным пиром заняла ~45 мс, повторный `add` из сохранённого кэша —
  ~4 мс. В R3 такая же перекачка занимала ~20 с. Различие: при re-add в R3
  `initial_peers` не передавались (блок `refetch_options` в
  `tools/engine-spike/src/main.rs`), пир находился через трекер. Возможно,
  перенесённые ~20 с — это заново найденные пиры, а не storage; проверить в R5.
- Границы охранной проверки: добавлено ребро `engine → cache`, `anyhow`
  разрешён только в `rustorr-engine` (сигнатуры `TorrentStorage` его требуют).
  Проверка `openssl` теперь идёт по `--target all` и включает `openssl-sys`.
  `openssl-probe` в `Cargo.lock` — не OpenSSL, а искатель системных
  сертификатов на чистом Rust.

### Шаг 5 — состояние в SQLite (выполнен 2026-09-21)

- Артефакты: `crates/rustorr-state/` (`State`, `CatalogEntry`, `ViewedEntry`,
  `Error`, схема v1 и раннер миграций в `schema.rs`); `rusqlite` и
  `libsqlite3-sys` закреплены за `rustorr-state` в `check-boundaries.py`.
- Проверено: `tools/r4.sh check` — код 0; state 36 тестов, всего по
  workspace 133. Мутации, каждая убита тестами: неверный `application_id`
  (падают 8 тестов), миграция без транзакции (ровно
  `a_failing_migration_rolls_back…`), снятый `CHECK json_valid`, `INSERT`
  вместо upsert, `remove_viewed` без фильтра по хешу, убранный `ORDER BY`,
  отключённая защита от чужой базы, отключённый WAL. Первая версия мутации
  миграции не собиралась (перемещение `&mut Connection` в цикл); результат
  засчитан только после исправленного повтора.
- Схема v1 выведена из корпуса эталона (`20260920T144518Z`), а не придумана:
  `timestamp` — секунды Unix, `torrent_size`; записи `/viewed` содержат
  `timecode`, поэтому у `viewed` есть колонка `timecode REAL` (тип числа в
  эталоне неизвестен; `REAL` принимает и целые, так что это безопасное
  надмножество); настройки — один JSON-документ из 41 ключа с вложенным
  `TMDBSettings`, читаемый и заменяемый целиком, поэтому хранятся одним
  текстом. Поле `data` в `torrents` взято из знания API TorrServer: в корпусе
  его нет, потому что оно опускается, когда пусто, — **не подтверждено
  корпусом**.
- Решения:
  - Настройки хранятся дословно (`CHECK json_valid`), без пересериализации:
    порядок ключей и пробелы возвращаются как записаны. Типизация — R7.
  - `viewed` не связан с каталогом внешним ключом: в эталоне это отдельное
    хранилище, а каскад при удалении торрента — решение контракта R6.
  - `.torrent` лежит в отдельной колонке, список каталога её не читает.
    `metainfo NOT NULL`: торрент без метаданных в каталог не попадает. Если
    R5/R6 понадобятся записи «сохранён до получения метаданных», это новая
    миграция.
  - Версия схемы — `PRAGMA user_version`, признак «наша база» —
    `PRAGMA application_id` («RSTR»). Чужой файл и база от более нового
    Rustorr отвергаются **до** любых изменений (WAL не включается). Каждая
    миграция — своя транзакция; упавшая не оставляет следов.
  - `synchronous` оставлен по умолчанию (`FULL`): записи редкие, а потеря
    только что сохранённых настроек при сбое питания хуже пары миллисекунд.
  - API синхронный, одно соединение за мьютексом; из async-кода вызывать на
    blocking-потоке.
- Найденная ошибка: `application_id` в SQL я сначала записал числом, посчитанным
  вручную (`1381258322`), а константа `0x52535452` равна `1381192786`. Иначе
  `open` не узнал бы собственную базу при втором запуске. Число проверено в
  Python; тесты теперь сравнивают константу с тем, что записала миграция.
- Не проверено и не сделано: WAL на сетевой файловой системе и на bind mount
  Docker (`journal_mode` там может остаться `delete`; корректность
  сохраняется, но это вопрос R9); online backup API — R9; сборка bundled
  SQLite под `x86_64` — шаг 8 (нативно на `aarch64` собирается).

### Шаг 6 — HTTP (выполнен 2026-09-21)

- Артефакты: `crates/rustorr-http/` (`router`, `ServerInfo`, `ApiError`,
  `with_layers`); `axum`, `tower*` закреплены за `rustorr-http` в
  `check-boundaries.py`.
- Проверено: `tools/r4.sh check` — код 0; http 11 тестов, всего по workspace
  144. Мутации, каждая убита предназначенным тестом: убранный fallback для
  неверного метода, не снятый `Allow`, query в логе, паника снаружи
  трассировки, `charset` у текстового 404, другой ключ в JSON-ошибке.
- Формы ошибок взяты из корпуса эталона (`20260920T144518Z`): неизвестный
  путь — `404`, `Content-Type: text/plain` (без charset), тело
  `404 page not found`; ошибка JSON-API — `400`, `{"error":"…"}`,
  `application/json; charset=utf-8`; часть `400` — без тела.
- Находки:
  - **Неверный метод на известном пути в эталоне — `404`, не `405`**
    (`GET /settings`, `/viewed`, `/cache`). Реализовано через
    `method_not_allowed_fallback`.
  - **axum всё равно добавляет `Allow` к такому ответу**, и делает это в
    `RouteFuture::poll`, то есть снаружи любых слоёв самого `Router`. Слой
    внутри роутера заголовок не видит. Маршруты поэтому смонтированы как
    fallback-сервис внешнего роутера, а `Allow` снимается снаружи. Заметил это
    тест, который я написал «на всякий случай»; в эталоне `Allow` нет.
  - **`/echo` в корпусе R2 нет.** Ответ (текст с версией) взят из знания API
    TorrServer и не подтверждён (пользователь принял это как допущение
    2026-09-21 до снятия сценария с эталона). Клиенты используют `/echo` для распознавания
    сервера, поэтому формат версии — решение совместимости R6, а не
    косметика. Сценарий нужно добавить в `tools/contract/scenarios.json` и
    снять с эталона (образ `rustorr-r1-torrserver` сохранился локально).
  - `Connection: close` в ответах корпуса — эхо клиента Python `urllib`, а не
    поведение эталона; копировать его не нужно.
- Решения:
  - Порядок слоёв, снаружи внутрь: трассировка, затем (R6) CORS/WAF/auth,
    затем перехват паник. Паника становится обычным `500`, проходит через
    внешние слои и попадает в лог со статусом.
  - В лог пишутся метод и **путь без query**: ссылки на торренты содержат
    URL трекеров с passkey, а критерий R9 — «нет секретов в логах». Тест
    проверяет, что `passkey` и `magnet` в лог не попадают.
  - `500` при панике — пустой ответ. В корпусе такого случая нет,
    поэтому это допущение, не характеризация.
  - Преобразование ошибок нижних crates (`cache`, `state`, `engine`) в ответы
    не написано: статус и форма зависят от маршрута и берутся из корпуса, а
    маршрутов в R4 нет. Это делается вместе с маршрутами в R6.
  - Зависимости `rustorr-http` от `engine`/`cache`/`state` в `Cargo.toml`
    пока не используются: `router` принимает только `ServerInfo`. Они
    остаются, потому что граф разрешён таблицей границ и понадобится R6.

### Шаг 7 — бинарник `rustorr` (выполнен 2026-09-21)

- Артефакты: `crates/rustorr-server/` (`config.rs`, `logging.rs`, `run.rs`,
  `main.rs`, `tests/process.rs`); `rustorr_http::serve`, чтобы бинарнику не
  нужна прямая зависимость от axum; `anyhow` разрешён в `rustorr-server` в
  `check-boundaries.py`.
- Проверено: `tools/r4.sh check` — код 0; всего 165 тестов (cache 52, domain
  20, engine 25, http 12, state 36, server 11 модульных и 9 процессных).
  Процессные тесты запускают настоящий бинарник: запрос, `SIGTERM`, `SIGINT`,
  порядок остановки по логам, перезапуск на том же data dir с проверкой, что
  сохранённые данные не тронуты, зависшее соединение, порт занят, data dir
  недоступен, файл не является базой, `--version` и неверные аргументы.
  Release-сборка (`lto = "thin"`): 16 МБ на `aarch64`, запускается, отвечает
  на `/echo`, на `SIGTERM` завершается с кодом 0.
- Мутации, каждая убита своим тестом: нет обработки `SIGINT`; нулевой срок
  ожидания; создание data dir до bind порта; неверное имя файла базы; потеря
  цепочки причин в сообщении об ошибке; код `FAILURE` при успехе.
- Проектные решения:
  - **Порядок запуска и отказ до побочных эффектов.** Обработчики сигналов,
    затем bind порта, затем data dir, база, кэш, движок. Занятый порт даёт
    код 1 и **не создаёт data dir** (проверено). Остановка идёт в обратном
    порядке независимо от причины: HTTP, движок, база.
  - **Срок ожидания при остановке.** `axum::serve` после сигнала безусловно
    ждёт завершения всех соединений (`close_tx.closed()`), поэтому один
    открытый видеопоток не давал бы серверу остановиться до `SIGKILL`.
    `stop_within` ограничивает ожидание `--shutdown-grace` (по умолчанию 5 с:
    меньше 10 с, которые Docker даёт на `stop`). Проверено на процессе:
    hyper считает недописанный запрос занятым соединением, срок срабатывает,
    в логе `open connections did not finish in time and were closed`.
  - **Явный runtime.** Только multi-thread (на current-thread движок выполняет
    блокирующую работу с диском прямо в потоке), и `shutdown_timeout(2 с)`,
    чтобы зависшая блокирующая задача не удерживала процесс.
  - Конфигурация: флаги и переменные `RUSTORR_*`; размер кэша принимает число
    или `KiB/MiB/GiB/TiB` и отвергает `GB`, чтобы не гадать между 10⁹ и 2³⁰.
    Логи в stderr, `RUST_LOG`, текст или JSON. Порт по умолчанию 8090, как у
    эталона. Флаги совместимости с CLI TorrServer — вопрос R9.
  - Кэш создаётся, но с движком пока не соединён (`CacheStorageFactory` не
    передаётся сессии): это R5.
- **Найденная ошибка шага 6.** Тест `a_panic_is_logged…` в `rustorr-http`
  оказался нестабильным: 9 падений из 60 запусков в параллельном режиме и 0 из
  60 в последовательном. Я объявил его зелёным по одному прогону, а мутация
  доказывала лишь, что он умеет падать, не что он стабилен. Причина: в
  параллельных тестах потоко-локальные подписчики `tracing` теряли события
  (гонка за кэш «интереса» callsite'ов). Исправлено: один глобальный
  подписчик на тестовый бинарник и последовательное выполнение тестов с
  запросами. После исправления 0 падений из 100. Процессные тесты проверены
  так же: 0 из 15.
- Ошибка измерения. Первый цикл проверки процессных тестов дал 15 из 15
  падений, потому что `env!("CARGO_BIN_EXE_rustorr")` зашивает путь
  `/cache/target/…` на этапе сборки, а volume я смонтировал в другое место.
  Это не флак; на правильном монтировании 0 из 15.
- Наблюдения для R9/R10:
  - librqbit при каждом старте предупреждает: `couldn't set UDP rcv buf size`
    (просил ~160 МиБ, получил 8 МиБ при `rmem_max` 8 МиБ). Влияет на uTP; на
    целевом сервере нужно смотреть `net.core.rmem_max`.
  - При остановке в лог попадает `error accepting uTP: dispatcher dead`
    (WARN, безобидно), и остановка занимает не меньше ~1 с из-за
    безусловного `sleep(1s)` в `Session::stop`.
  - Логи librqbit идут в тот же поток (`librqbit::*`); решение о фильтрации —
    R9.
  - `--peer-port 0` выбрал один порт для TCP и UDP.
  - Не проверено: что движок действительно остановил свои задачи, наблюдаемо
    только через порядок наших сообщений и отсутствие зависания; формат ответа
    `/echo` (см. шаг 6).
