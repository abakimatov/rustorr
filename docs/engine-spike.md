# Engine spike R3

Статус: `all R3 gates closed; ADR 0003 records adopt`

Точка продолжения для новой сессии —
[`docs/r3-continuation.md`](r3-continuation.md).

Spike изолирован в `tools/engine-spike/` и сейчас нацелен на `librqbit`
`9.0.1`. Он не реализует HTTP-маршруты Rustorr и production-поведение кэша.
Проба фиксирует метаданные, отображение файлов, позиционное чтение,
одновременные просмотры, задержку перемотки, отмену, конфигурацию сохранения и
пользовательские колбэки чтения/записи хранилища.

## Воспроизводимый прогон

Docker-overlay переиспользует фикстуры, трекер и сидер R1:

```sh
tools/engine-spike/run.sh doctor
tools/engine-spike/run.sh config
tools/engine-spike/run.sh build
tools/engine-spike/run.sh probe --offset 0 --length 262144
tools/engine-spike/run.sh probe --offset 4194304 --length 262144 --custom-storage
tools/engine-spike/run.sh probe --magnet 'magnet:?xt=urn:btih:68c3ccdd52b2925f4f97e2f61ea248e728e54cea&dn=single&tr=http%3A%2F%2Ftracker%3A6969%2Fannounce' --disable-dht
tools/engine-spike/run.sh probe --views 3 --disable-dht
tools/engine-spike/run.sh probe --utp-only --disable-dht
tools/engine-spike/run.sh probe --custom-storage --delete-and-refetch
tools/engine-spike/run.sh probe --disable-dht --custom-storage --evict-after-read \
  --offset 4194304 --length 262144
tools/engine-spike/run.sh probe --disable-dht --warmup-offset 0 \
  --offset 4194304 --length 262144
tools/engine-spike/run.sh pex --offset 4194304 --length 262144 --pex-observe-ms 90000
tools/engine-spike/run.sh down
```

Сырые результаты пишутся вне репозитория в
`${RUSTORR_ENGINE_SPIKE_RUN_ROOT:-/tmp/rustorr-engine-spike}`. Раннер
сохраняет матрицу сценариев R1 рядом с каждой пробой, чтобы будущая агрегация
матрицы могла использовать те же ID сценариев и пороги паритета.

## Текущие гейты

- Метаданные и отображение файлов должны быть доступны после инициализации.
- Возвращённые байты должны совпадать с ожидаемым SHA-256, если он задан.
- Перемотка и позиционное чтение должны завершаться без неудачных запросов.
- `--cancel-after-ms` должен сбросить поток, не удерживая процесс живым.
- `--persistence PATH` включает путь сохранения сессии кандидата для
  экспериментов с перезапуском.
- `--custom-storage` должен вызывать колбэки хранилища.
- `--views N` должен выполнить N одновременных позиционных чтений в одной
  сессии и вернуть ожидаемый дайджест для каждого просмотра.
- `--delete-and-refetch` должен удалить и заново добавить торрент, а затем
  вернуть те же байты после новой загрузки. Это гейт удаления/повторного
  добавления в сессии, а не доказательство вытеснения на уровне кусков:
  `librqbit 9.0.1` не предоставляет публичного API для вытеснения отдельных
  кусков за своим chunk tracker.
- `--evict-after-read` обнуляет прочитанный диапазон на диске под живым
  торрентом и читает его снова. Этот гейт диагностический, а не pass/fail: он
  фиксирует, что делает движок, когда принадлежащее Rustorr хранилище теряет
  данные.
- `run.sh pex` должен показать, как клиент с отключёнными на уровне сессии
  трекерами и DHT обнаруживает пир, который ему никогда не передавали, и
  загружает с него данные. Соответствующий контроль без начального пира не
  должен найти ни одного пира.

Решение записано в [ADR 0003](adr/0003-bittorrent-engine-selection.md):
`adopt` с фиксацией `librqbit = 9.0.1` за адаптером Rustorr.

## Доказательства выполнения 2026-09-20

Все пробы запускались в Docker с трекером/сидером R1, отключённым DHT и
ограниченными таймаутами инициализации/чтения. Сырой вывод лежит в
`/tmp/rustorr-engine-spike/` и намеренно не коммитится.

- Известный торрент, файловое хранилище по умолчанию: два новых независимых
  прогона (`20260920T163634Z` и `20260920T164148Z`) вернули ожидаемый SHA-256
  для 65,536 байт
  `31e67ed8a3c058d5d68dfac1cd83c24b6ade45ffea0f7833d8eaa3951eae643b`;
  каждый прогон видел один живой TCP-пир и один загруженный кусок.
- Перемотка/чтение: новое чтение по смещению `4194304` вернуло ожидаемый
  SHA-256
  `210ba6b19ee6a72f875261cd3a41d030fad18470c0fc633ee61b1a7d84174795`.
- Три одновременных просмотра вернули ожидаемые байты и видели сидирующий
  пир; инициализация/чтение заняли около `9.92 s` на просмотр.
- Пользовательское хранилище: то же чтение известного торрента прошло с
  записывающими колбэками (`creates=1`, `inits=1`, `takes=1`, `writes=20`,
  `reads=6`, `completed_pieces=1`).
- Удаление/повторная загрузка: удаление и повторное добавление прошли и
  вернули тот же хеш; счётчики показали два создания хранилища, две
  инициализации и два завершённых куска. Повторная загрузка заняла около
  `20.1 s`, так что это функциональное доказательство, но ещё не точка
  приёмки производительности.
- Отмена: чтение, отменённое через `1 ms`, вернуло результат отмены примерно
  за `2 ms`, и процесс корректно завершился.
- Метаданные magnet: magnet с локальным трекером получил метаданные и вернул
  тот же ожидаемый дайджест; весь прогон — добавление, получение и чтение —
  занял около `25.2 s`. Само получение позже было измерено отдельно —
  `2855.9 ms`; см. перемер с совпадением состояния ниже.
- Перезапуск с сохранением: два процесса использовали один каталог
  сохранения; когда второй процесс использовал исходный выходной путь,
  инициализация восстановила `262144` байт, и чтение заняло `3.7 ms` без
  живого пира. Это доказывает полезный путь fast-resume для того же выходного
  каталога, но не общую политику вытеснения кэша.

Healthcheck сидера baseline намеренно требует двух известных фикстур R1,
используемых этим spike. Unicode-фикстура остаётся `0% None` в Transmission и
не используется как входные данные R3.

## Доказательства выполнения 2026-09-21 — peer exchange

`run.sh pex` строит в сети R1 топологию из трёх узлов: сидер Transmission,
пир librqbit `pex-middle`, который знает трекер и слушает фиксированный порт
`46900`, и `pex-client` с выключенными DHT и LSD, отключёнными на уровне
сессии трекерами и ровно одним начальным пиром — `pex-middle`. Любой другой
адрес, оказавшийся у клиента, мог прийти только через PEX. Промежуточный пир
ограничен по скорости (`--upload-limit-bps 65536`,
`--download-limit-bps 131072`), чтобы он всё ещё активно скачивал и,
следовательно, имел живой исходящий пир для анонса, пока клиент подключён.
Флаги пробы для этого — `--initial-peers HOST:PORT,...`,
`--disable-trackers`, `--listen-port`, `--upload-limit-bps`,
`--download-limit-bps`, `--pex-observe-ms`, `--wait-complete-ms` и
`--result-file`; `rustorr-engine-spike --help` перечисляет все флаги.

| прогон | обнаружено пиров | байт от найденного через PEX сидера | байт от начального пира | дайджест |
| --- | ---: | ---: | ---: | --- |
| `pex-20260920T175048Z` | 3 | 8,126,464 (31 кусок) | 262,144 (1 кусок) | ожидаемый |
| `pex-20260920T175326Z` | 3 | 8,126,464 (31 кусок) | 262,144 (1 кусок) | ожидаемый |

Отрицательный контроль `pex-control-20260920T174652Z` запустил того же
клиента без начального пира и упал с `deadline has elapsed`, не найдя ни
одного пира. Именно контроль делает результат атрибутируемым: более ранняя
попытка `pex-20260920T174321Z` выглядела успехом PEX, но была
недействительной, потому что `librqbit 9.0.1` игнорирует
`AddTorrentOptions::disable_trackers`, и «скрытый» клиент продолжал
анонсироваться трекеру. Список трекеров очищает только
`SessionOptions::disable_trackers`. Ещё два прогона записаны, но заменены:
`pex-20260920T173959Z` (та же утечка трекера) и `pex-20260920T174800Z`, где
промежуточный пир уже завершил загрузку, убрал сидер из набора живых
исходящих пиров и поэтому ничего не анонсировал — клиент никого не
обнаружил.

## Доказательства выполнения 2026-09-21 — вытеснение хранилища под живым торрентом

`--evict-after-read` читает диапазон, проверяет его дайджест, обнуляет ровно
этот диапазон на диске, пока торрент остаётся живым, и читает его снова через
тот же handle.

| прогон | первое чтение | после вытеснения | восстановлено |
| --- | --- | --- | --- |
| `20260920T175558Z` | `210ba6b1…` за 3870.2 ms | `8a39d2ab…` за 1.2 ms | нет |
| `20260920T175634Z` | `210ba6b1…` за 3859.0 ms | `8a39d2ab…` за 0.9 ms | нет |

Движок не выдал ошибку и не загрузил данные заново: он отдал обнулённые
байты. Именно этот результат фиксирует гранулярность вытеснения Rustorr на
уровне торрента в [ADR 0004](adr/0004-cache-eviction-seam.md).

## Доказательства выполнения 2026-09-21 — перемер с совпадением состояния

Две отмеченные строки оказались сравнением разных величин. R1 замеряет
перемотку только после того, как торрент добавлен, метаданные получены, сидер
подключён и первый диапазон отдан; метрика magnet в R1 останавливается на
«появился в списке с подключённым сидером» и никогда не включает чтение.
Перемер по этим протоколам:

| замер | результат R3 | эталон R1 | источник |
| --- | ---: | ---: | --- |
| перемотка после прогревочного чтения (`--warmup-offset 0`) | 500.2 / 505.2 ms | `seek-loaded` 4512.8 ms | `20260920T181105Z`, `20260920T181129Z` |
| только получение метаданных magnet | 2855.9 ms | `cold-magnet-metadata` 6058.5 ms | `20260920T181310Z` |
| реальная инициализация, вход `.torrent` | 1.4 ms | н/п | те же прогоны |

Два вопроса не разрешились и переносятся в R4: первое чтение после получения
magnet заняло `20597.9 ms` против `3.8 s` из файла `.torrent`, а повторная
загрузка на уровне торрента стоит около `20.1 s`. Сходство указывает на общую
причину в повторном поиске пиров после повторного добавления; порога R1 нет
ни у одного.

Теперь проба корректно сообщает `initialized_ms` и добавляет `total_ms` и
`warmup_read`.

## Сопоставление с метриками R1

Правило сравнения и таблица по сценариям находятся в
[engine-r1-metric-mapping.md](engine-r1-metric-mapping.md). Кратко: тайминги
движка — нижняя граница полного пути Rustorr, поэтому они могут исключить
кандидата, но никогда не объявляют паритет, и имеют смысл только там, где
совпадает предусловие состояния R1. Три строки — холодная перемотка,
метаданные magnet и повторная загрузка на уровне торрента — выше ближайшего
эталона R1 и переносятся в R4 как открытые риски производительности.

## Контрольная точка 2026-09-21

Завершено и проверено:

- зафиксированная версия toolchain Rust `1.90.0`;
- зафиксированная зависимость `librqbit = 9.0.1`;
- сгенерирован `tools/engine-spike/Cargo.lock` с 362 разрешёнными пакетами;
- валидация Docker Compose overlay;
- release-сборка во внутренней файловой системе Docker;
- запуск бинарника и вывод `--help`;
- синтаксис shell, rustfmt, clippy с `-D warnings` и `git diff --check`.

Release-сборка завершилась как `rustorr-engine-spike` в образе
`rustorr-r1-engine-spike`. Первая попытка сборки через bind mount хоста
получила SIGBUS в rustc ещё до диагностики проекта, поэтому Dockerfile теперь
собирает в слое образа, чтобы обойти этот путь файловой системы.

Прерванная ранее проба `/tmp/rustorr-engine-spike/20260920T153748Z`
остаётся недействительной и не используется. Первая ограниченная серия тоже
использовала устаревший том сидера и исключена из доказательств выше; новая
серия запущена после перезапуска фикстур/сидера. Последующие ограниченные
прогоны, перечисленные выше, — действительные доказательства функциональности
и повторяемости. Ни паритет производительности HTTP/плеера, ни возможность
вытеснения хранилища на уровне кусков не приняты. Гейты DHT bootstrap,
передачи через uTP и peer exchange подтверждены отдельно в артефактах выше, а
вывод о выборе движка записан в ADR 0003.

## Контрольная точка 2026-09-21 — R3 закрыт

Три оставшихся гейта закрыты: peer exchange подтверждён с отрицательным
контролем, seam вытеснения кэша определён в ADR 0004, а правило сравнения
движка с R1 записано. ADR 0003 фиксирует `adopt`.

Всё ещё не установлено и намеренно перенесено дальше:

- для кандидата нет ни одного замера HTTP Range или плеера с декодированием;
  пороги R1 по-прежнему ничем в R3 не сопоставлены;
- первое чтение после получения magnet и повторная загрузка на уровне
  торрента стоят около 20 s и не объяснены; холодная перемотка и метаданные
  magnet перемерены с совпадением состояния и уверенно ниже эталонов R1;
- вытеснение на уровне кусков остаётся невозможным без upstream-изменения,
  что и является названным триггером форка.
