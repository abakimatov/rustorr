# Сопоставление замеров движка R3 с метриками R1

Статус: `accepted as the comparison rule for R3`

R3 измеряет чтение librqbit внутри процесса. R1 измерял TorrServer через HTTP.
Это разные величины, поэтому документ точно определяет, как числа R3 можно и
нельзя использовать и какая работа закрывает разрыв.

## Что на самом деле измеряет каждая сторона

| | Baseline R1 | Engine spike R3 |
| --- | --- | --- |
| Поверхность | HTTP `GET`/Range против TorrServer в Docker | `handle.stream(file).seek().read_exact(n)` внутри процесса |
| Включённый путь | сеть контейнеров, HTTP-фрейминг, кэш TorrServer и планирование кусков | только планирование кусков и хранилище движка |
| Протокол состояния | явные предусловия `empty`/`warm`/`loaded`/`missing`/`evicted` для каждого сценария | новая сессия на каждый прогон плюс один случай fast-resume в тот же каталог |
| Старт клиента | измеряется раннером R1 | не измеряется |
| Старт плеера / ребуферизация | не измеряется (транспортные остановки — лишь прокси) | не измеряется |
| Замер ресурсов | контейнер TorrServer | контейнер spike, без HTTP- и кэш-слоя |

Поскольку путь R3 — строгое подмножество пути R1, тайминг R3 — это **нижняя
граница** стоимости того же сценария через HTTP-поверхность Rustorr.

## Правило сравнения

1. Тайминги R3 можно использовать, чтобы **исключить кандидата**: если один
   движок не может превзойти порог R1, полный путь Rustorr тоже не сможет.
2. Тайминги R3 **никогда** нельзя использовать для объявления паритета,
   потому что в них нет HTTP-, кэш- и плеерного слоёв, которые входят в
   пороги.
3. Сравнение имеет смысл только тогда, когда предусловие состояния сценария R1
   совпадает с состоянием прогона R3. Прогоны R3 с холодной сессией нельзя
   сравнивать со строками R1 `warm` или `loaded`.
4. Паритет объявляется только прогоном `tools/baseline/r1.sh` против
   HTTP-поверхности Rustorr, дающим те же ID сценариев, что и
   `tools/baseline/scenarios.json`. Это работа R4/R5, а не R3.

Каждый прогон spike уже копирует `scenarios.json` рядом со своим сырым
выводом, чтобы будущую матрицу можно было агрегировать по тем же ID
сценариев.

HTTP- и кэш-слоя, поэтому это нижняя граница потребления Rustorr, а не его
прогноз.

## Как были сняты прежние флаги

Более ранняя редакция документа отмечала холодную перемотку, метаданные magnet
и повторную загрузку как превышающие эталоны R1. Два из трёх случаев оказались
артефактами сравнения разных величин, и перемер по собственному протоколу R1
их устранил:

- **Перемотка.** R1 замеряет перемотку только *после* того, как торрент
  добавлен, метаданные получены, сидер подключён и первый диапазон уже отдан.
  Прогоны перемотки R3 включали всё это в число. Повторный запуск с
  `--warmup-offset 0` воспроизводит протокол R1:
  `/tmp/rustorr-engine-spike/20260920T181105Z` и `20260920T181129Z` дают
  `500.2 ms` и `505.2 ms` против порога `4512.8 ms`.
- **Magnet.** `metadata_discovery_ms` в R1 останавливается, когда торрент
  появляется в списке с подключённым сидером; чтение туда никогда не входит.
  Число R3 включало полное чтение 256 KiB. Измеренный отдельно прогон
  `/tmp/rustorr-engine-spike/20260920T181310Z` получил метаданные magnet за
  `2855.9 ms` против порога `6058.5 ms`.
- **Повторная загрузка.** Этот случай не снят и тоже несопоставим: R3 удаляет
  и заново скачивает целый торрент (~20.1 s), тогда как строка R1
  `seek-evicted` лишь устанавливает холодную карту кусков, потому что
  TorrServer не предоставляет детерминированного API вытеснения. См.
  [ADR 0004](adr/0004-cache-eviction-seam.md).

Остаются два настоящих открытых вопроса, на оба ответит R4:

1. Первое чтение после получения magnet заняло `20597.9 ms` — намного дольше
   первого чтения `3.8 s` из файла `.torrent`. R1 этого не измерял, порога
   нет, но разрыв реален и не объяснён.
2. Повторная загрузка на уровне торрента стоит около `20.1 s` — достаточно
   близко к цифре magnet выше, чтобы предполагать общую причину, скорее всего
   повторный поиск пиров после повторного добавления. Стоит диагностировать до
   выбора лимита кэша.

### Дефект измерения, найденный в процессе

Поле spike `initialized_ms` вычислялось в конце прогона, поэтому показывало
добавление + инициализацию + чтение + все последующие фазы, а не
инициализацию. Теперь оно останавливается сразу после
`wait_until_initialized`, а полную длительность несёт отдельное `total_ms`.
Реальная инициализация — `1.4 ms`; все цифры с подписью «initialized ms» в
прежней матрице повторов фактически были общим временем прогона, поэтому они
и были так близки ко времени чтения.

## Что закрывает разрыв

1. R4 строит HTTP Range-поверхность Rustorr над адаптером движка.
2. `tools/baseline/r1.sh` без изменений запускается против этой поверхности и
   даёт строки с теми же ID сценариев и теми же предусловиями состояния.
3. С `rustorr_targets` сравниваются именно эти строки, а не тайминги проб R3.
4. Старт и ребуферизация на уровне плеера остаются отдельной задачей
   характеризации и в R1, и в R4; транспортные остановки по-прежнему
   помечаются как прокси.
